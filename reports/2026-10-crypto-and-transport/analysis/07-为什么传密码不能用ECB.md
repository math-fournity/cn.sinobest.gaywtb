# 为什么传输密码不能用 ECB —— 写给「懂计算机、不懂密码学」的读者

> 主报告说「用 ECB 加密密码有问题」，但**问题到底在哪**、危害有多大，
> 需要单独讲清楚。本文件只回答一个问题：
>
> **即使攻击者暂时拿不到那把写死的密钥，用 ECB 传密码为什么仍然不安全？**
>
> 结论先给：**因为 ECB 是确定性的——同样的密码永远产生同样的密文。
> 这一条本身就足以泄露信息，与密钥是否泄露无关。**

---

## 0. 先划清范围：本项目里两个 ECB 场景，危害不同

必须先说清楚，否则会夸大或缩小问题。

| 场景 | 平台 | 加密什么 | 危害等级 |
|---|---|---|---|
| **中科江南 H5** | iOS（本报告对象） | **用户密码**（还有手机号、验证码） | **高**——见 §1 起 |
| **云从科技 SDK** | Android / iOS | **活体检测数据**（`sm4EncHackStr`、`wMd5Sm4`、`cwGetEncryptDataAndPubkeyIndex`），**不是密码** | **中**——见 §6 |

**本文件 §1~§5 讲的是「密码」场景**，也就是中科江南那一端。
云从那一端的分析在 §6，它的危害**不能照搬密码场景**。

---

## 1. 核心问题：ECB 是「确定性」加密

### 1.1 什么叫确定性

| 加密方式 | 同一段明文，加密两次 | 结果 |
|---|---|---|
| **ECB** | `"123456"` → `A`；`"123456"` → `A` | **永远相同** |
| CBC / GCM（正确做法） | `"123456"` → `A`；`"123456"` → `B` | **每次不同**（因为每次用不同的随机 IV/Nonce） |

**为什么 CBC/GCM 能做到不同**：它们在加密前掺入一个随机数（IV/Nonce），
所以同一明文每次的输出都不一样。

**ECB 没有这个随机数。** 它把每个 16 字节块独立地、用同一把钥匙、同样的方式加密。
**同样的输入，必然得到同样的输出。**

### 1.2 这条性质为什么致命

**关键洞察**：攻击者**不需要解密**，只需要**比较密文是否相等**。

```
密文 A 出现了 5 万次  →  说明有 5 万个用户用了同一个密码
密文 B 出现了 3 万次  →  说明有 3 万个用户用了同一个密码
密文 C 只出现 1 次    →  说明这个密码很独特
```

**这不需要密钥，不需要解密，不需要任何密码学知识。** 只需要一个计数器。

---

## 2. 三种不需要密钥的攻击

### 2.1 攻击一：密码复用识别（最直接）

**攻击者能知道什么**：哪些用户用了**完全相同的密码**。

**为什么这有害**：

- 如果你知道「用户 X 和用户 Y 的密码密文相同」，那么**攻破其中一个就等于攻破两个**；
- 撞库攻击的效率成倍提高——不必逐个账号试，而是**按密文分组批量试**；
- 一个密码泄露（比如用户在别处泄露了），**同组所有账号同时沦陷**。

**这在真实事件中发生过**：2013 年 Adobe 数据泄露，1.5 亿用户记录外泄。
泄露数据里密码是加密存储的，但因为用了 ECB 类确定性加密，
安全研究者**仅凭「哪些密文相同」就分出了大量密码组**，再结合密码提示
（password hint）还原出海量明文密码。

> **注意**：Adobe 那次是**存储**场景，本报告是**传输**场景。
> 两者的共同点是「确定性加密 + 大量样本」；不同点是攻击者获取密文的渠道
> （存储泄露 vs 流量/日志截获）。**原理相同，渠道不同。**

### 2.2 攻击二：频率分析（缩小暴力破解范围）

**攻击者能知道什么**：哪个密文出现得最频繁。

**为什么这有害**：

- 真实世界的密码分布是**极不均匀**的——`123456`、`password`、`888888`、
  手机号后六位这类弱密码占据很大比例；
- 所以**出现频率最高的那几个密文，几乎必然对应最常见的弱密码**；
- 攻击者不需要解密，就能排出「优先试哪些密码」的顺序。

**这把暴力破解的空间从「所有可能的密码」压缩到「最常见的几百个」。**

```
攻击者观察到的密文频次分布（示意）：
  密文 A: 50,000 次   ← 优先试 123456 / password / 111111
  密文 B: 30,000 次   ← 其次
  密文 C: 12,000 次
  ...
  密文 Z: 1 次        ← 最后再管
```

**用户量越大，这个统计越准。** 一个部级政务 App 的用户量，足以支撑这种分析。

### 2.3 攻击三：已知明文确认（最精准）

**攻击者能知道什么**：某个特定用户的密码，是不是某个已知值。

**怎么做到**：

1. 攻击者自己注册一个账号，把密码设成 `123456`；
2. 他截获自己这条请求的密文，记下来（假设是 `A`）；
3. 之后他在流量里看到**别人的密文也是 `A`**；
4. ⇒ **那个人的密码就是 `123456`**。

**这不需要密钥，也不需要解密。** 攻击者只是「自己造一个样本，然后去比对」。

**更糟的是**：如果攻击者能构造任意密码并观察密文（比如他能注册账号），
他可以**离线预先建一张「常用密码 → 密文」对照表**，然后拿去匹配所有截获的密文。
这张表**算一次就能永久复用**，因为 ECB 是确定性的。

## 3. 还有其他不需要密钥的泄露

| 泄露 | 机制 | 严重度 |
|---|---|---|
| **长度泄露** | PKCS7 填充使密文长度反映明文大致长度（密码 8 位 vs 16 位，密文长度不同） | 中 |
| **块结构泄露** | 超过 16 字节的密码被分块，重复的块在密文里也重复 | 中 |
| **重放风险** | 若请求无时间戳/随机数/完整性校验，密文可被直接重放 | **高**（见 §4） |

---

## 4. 重放：一个常被忽略但很实际的风险

**问题**：如果服务端只验「密文能否解密成正确密码」，而不校验
「这个请求是不是新鲜的」，那么**截获到的密文可以被原样重发**。

**具体到本 App**：登录请求体里有 `password`（ECB 密文）与 `encryption:"1"` 标记。
**本报告未验证服务端是否有防重放机制**（这需要服务端行为，超出静态分析边界）。
**列为开放问题。**

> **但有一点可以确定**：ECB 的确定性**使得**「同一密文重放」在语义上永远有效
> ——因为同一密码永远产生同一密文。CBC/GCM 至少会让每次的密文不同，
> 使「重放」在密文层面就可被识别。

---

## 5. 那「密钥没泄露」这个前提成立吗？

**本报告的立场：不成立，但即使成立，上面的问题依然存在。**

### 5.1 密钥其实已经泄露了

本报告 §2.1 已证：密钥 `385f33cb…9081ab7` **明文写在 H5 文件里**。

```
grep -o "385f33cb…9081ab7" www/p__login__Login.js
```

任何拿到这个 IPA 的人，一条命令就能取到。**这不是「可能泄露」，是「已经公开」。**

### 5.2 但即使假设密钥保密，问题仍在

这是本文件的核心论点：

| 前提 | 是否安全 |
|---|---|
| 攻击者没拿到密钥 | ❌ **仍不安全**——能通过密文相等性做密码复用识别与频率分析（§2） |
| 攻击者拿到密钥（现实中很容易） | ❌ **完全不安全**——所有密码可直接解密 |
| **正确做法** | 客户端**不做**对称加密；走 HTTPS + **服务端慢哈希**（Argon2id / scrypt / bcrypt） |

**关键**：把「加密」这件事放在客户端做，本身就是错的——
因为客户端的一切（包括密钥）都可被提取。**客户端加密不提供任何保密性。**

---

## 6. 云从 SDK 那一端：加密的不是密码，危害不同

**必须分开讲，否则会夸大。**

### 6.1 它加密什么

从 `libcloudwalk_sdk.so` 的符号看：

```
sm4EncHackStr               ← SM4 加密字符串
sm4EncHackStrWithRandomKey  ← 带随机钥的变体
sm4EncHackStr4HuaxiaCredit  ← 华夏信科定制变体
wMd5Sm4                     ← MD5 + SM4 组合
cwGetEncryptDataAndPubkeyIndex ← 加密数据 + 公钥索引
cwIbisSM4CheckLiveness      ← 活体检测链路
```

**这些都在活体检测/人脸数据的处理链路上，不是用户密码。**

### 6.2 危害为什么不同

| 维度 | 密码场景 | 活体数据场景 |
|---|---|---|
| 数据熵 | **低**（人选的密码，分布极不均匀） | **高**（人脸图像、特征向量） |
| 频率分析可行吗 | ✅ **可行**——弱密码大量重复 | ❌ 不可行——每张人脸都不同 |
| 已知明文确认 | ✅ 容易（自己注册即可） | 较难（需要构造特定人脸数据） |
| 复用识别 | ✅ 有意义（同密码即同密文） | 意义有限（同一张人脸重复上传才触发） |
| **主要危害** | 密码泄露 | **密钥泄露后可解密历史活体数据**（生物特征不可更换） |

**关键差异**：活体数据的**熵很高**，所以 ECB 的「同明文同密文」性质**很少被触发**
（不会有大量用户上传完全相同的图片）。

⇒ **云从那一端的 ECB 仍然是个缺陷**（NIST 明确不建议、且密钥硬编码），
但**危害程度低于密码场景**，不能直接类比。

### 6.3 但有一条仍然严重

**生物特征不可更换。** 一旦密钥泄露、历史活体数据被解密，
用户无法像改密码那样「换一张脸」。

⇒ 云从场景的正确表述是：**ECB + 硬编码密钥的组合，使得历史活体数据在密钥
泄露后永久可解，而生物特征无法轮换。** 这是与密码场景**不同性质**的风险。

---

## 7. 正确做法（说「不应该」必须答「该怎样」）

| 层次 | 正确做法 |
|---|---|
| **密码传输** | **不要在客户端加密密码**。走 HTTPS（TLS 已提供传输保密），到服务端后用**慢哈希**（Argon2id / scrypt / bcrypt / PBKDF2）存储 |
| **密码存储** | 慢哈希 + 每用户独立盐值。**永远不要**用可逆加密存密码 |
| **确需客户端加密的场景** | 用 **AES-GCM**（带认证，防篡改）或 **AES-CBC + 随机 IV**；密钥走 Keychain / Secure Enclave，不硬编码 |
| **活体/生物特征** | 同上；且应评估「是否必须留存原始生物特征」——多数场景只需留存比对结果 |

> **为什么慢哈希而不是加密**：密码的验证只需要「比对」，不需要「还原」。
> 慢哈希（如 Argon2id）故意设计得计算昂贵，使离线暴力破解成本极高。
> 加密（无论什么模式）都是可逆的，一旦密钥泄露即全部沦陷。

## 9. 复现

```bash
# 演示「同密码即同密文」
python3 ../code/ecb_demo.py

# 手工验证（用本 App 的真实密钥）
# 本报告密钥是脱敏的，先从 IPA 里取真值
KEY=$(grep -o '[0-9a-f]\{32\}' \
  "out/Payload/公安一网通办.app/www/p__login__Login.js" | head -1)
echo ${#KEY}        # 应为 32
KEYHEX=$(printf '%s' "$KEY" | xxd -p -c 256)
echo ${#KEYHEX}     # 应为 64（这一行是自检，别省——省了会用零填充静默算错）
printf '123456' | openssl enc -aes-256-ecb -K "$KEYHEX" -nosalt | xxd -p -c 256
printf '123456' | openssl enc -aes-256-ecb -K "$KEYHEX" -nosalt | xxd -p -c 256
# 两次输出完全相同 ⇒ 攻击者用计数器就能统计密码分布

# 对比：CBC 模式下同一明文两次结果不同
IV=$(openssl rand -hex 16)
printf '123456' | openssl enc -aes-256-cbc -K "$KEYHEX" -iv "$IV" -nosalt | xxd -p -c 256
IV2=$(openssl rand -hex 16)
printf '123456' | openssl enc -aes-256-cbc -K "$KEYHEX" -iv "$IV2" -nosalt | xxd -p -c 256
# 两次输出不同 ⇒ 无法通过密文相等性做统计
```

## 0. 先说一条被驳回的（重要）

我们原本想引用 **GB/T 17964-2021** 与 **GB/T 39786-2021** 的正文条款来论证
「ECB 不合规」。**对抗复核把这条路驳回了**，理由如下：

| 问题 | 详情 |
|---|---|
| **正文取不到** | 标准正文以**会话门控的页面图片**形式提供（`/bzgk/std/viewGbImg?fileName=…`），11 个分块全部返回 HTTP 302 / 0 字节 |
| **引用的 URL 不是正文** | `openstd.samr.gov.cn` 的那个 URL 只解析到一张**元数据卡片**（标准号、标题、状态、日期），正文 0 命中 |
| **locator 是编的** | 声称「正文第 N 页」的那些引文，无法在该 URL 上演示 |
| **两处张冠李戴** | GM/T 0054 的适用范围句在被引页面上不存在；GB/T 39786 的「第5章 a)」可能挂在第三方站自加的标题下 |

**复核者同时确认了几件真事**（这部分可用）：

- 《密码法》第八条 / 第二十四条 / 第二十七条 —— 与 OSCCA 官方文本**逐字一致**；
- 《商用密码管理条例》第三十八条 / 第三十九条 —— 与国务院公报**逐字一致**；
- **GM/Y 5001-2021** 两处引文（印刷页 10、18）—— 从官方 PDF 实取，**逐字一致**；
- 「附录 A 是资料性附录」「附录 B 是资料性附录」—— 官方 2023 版指南逐字确认。

⇒ **本报告的处理**：中国标准的**法律层面**（密码法、条例）照引；
**标准正文层面**（GB/T 17964 具体条款）**不引**，改注「原文未取得」。
这正是本报告 §0 那条纪律的实例：**宁可少说一个属性，不多说一个。**

## 1. ECB 工作模式

### NIST SP 800-38A §6.1（2001 版）

**出处**：`https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38a.pdf`
（66 页，PDF CreationDate 2001-12-10，Morris Dworkin）

> "The Electronic Codebook (ECB) mode is a confidentiality mode that features, for a
> given key, the assignment of a fixed ciphertext block to each plaintext block,
> analogous to the assignment of code words in a codebook."
> —— §6.1，印刷页 9（PDF 页 16），本节开篇句

> "In the ECB mode, under a given key, any given plaintext block always gets encrypted
> to the same ciphertext block."
> —— §6.1，印刷页 9-10（句子跨页）

> "If this property is undesirable in a particular application, the ECB mode should
> not be used."
> —— §6.1，印刷页 10

> "In ECB encryption, the forward cipher function is applied directly and
> independently to each block of the plaintext."
> —— §6.1，印刷页 9

### ⚠️ 引用边界（必须一并声明）

1. **它是建议性文献，不是强制标准。** 该文件印刷页 1 自述：
   *"neither a standard nor a guideline, and as such, is neither mandatory nor binding
   on Federal agencies"*。
   ⇒ 本报告只写「**NIST 建议**此类场景不应使用 ECB」，**不写「违反 NIST 标准」**。
2. **该文件全文不含 "diffusion" / "short data" 等表述**（复核者全文 grep 零命中）。
   「ECB 缺乏扩散、只适合短数据」是**密码学教科书通说，不是该文件原句**，
   本报告不将其挂在该文件名下。
3. 该文件唯一的 ECB 适用性警告是**条件式**的（"If this property is undesirable…"），
   不是绝对禁止。本报告按条件式引用。

## 2. 硬编码密钥 / 密钥管理

### 2.1 OWASP MASVS-CRYPTO-1 / CRYPTO-2（v2.1.0）

**出处**：`https://mas.owasp.org/MASVS/controls/MASVS-CRYPTO-1/`
（v2.1.0，2024-01-18 发布；master 上控制项文本字节一致）

> **MASVS-CRYPTO-1**：*"The app employs current strong cryptography and uses it
> according to industry best practices."*

> **MASVS-CRYPTO-2**：*"The app performs key management according to industry best
> practices."*

> CRYPTO-2 说明：*"Even the strongest cryptography would be compromised by poor key
> management. This control covers the management of cryptographic keys throughout their
> lifecycle, including key generation, storage and protection."*

> 章节引言：*"The purpose of the controls in this category is to ensure that the
> verified app uses cryptography according to industry best practices, which are
> typically defined in external standards such as NIST.SP.800-175B and
> NIST.SP.800-57."*

### 2.2 OWASP MASTG — **iOS 专用的硬编码密钥测试**

这是本报告**最直接**的规范依据，之前未找到：

> **MASTG-TEST-0213**（iOS，*Use of Hardcoded Cryptographic Key*）
> **判定标准**：*"**The test case fails if calls to cryptographic functions with
> hardcoded keys are found within binary.**"*
> —— `https://mas.owasp.org/MASTG/tests/ios/MASTG-TEST-0213/`

> **MASTG-TEST-0212**（Android 同题）判定标准：
> *"The test case fails if you find any hardcoded keys that are used in
> security-sensitive contexts."*

**意义**：MASTG 的判定是**发现即失败**（fails if found），不是「建议改进」。
本 App 的情况——`Utf8.parse("385f33cb…")` 直接作为 `AES.encrypt` 的密钥参数——
**精确命中**这个判定条件。

### 2.3 NIST SP 800-57 Part 1 Rev. 5（2020-05）

**出处**：`https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-57pt1r5.pdf`
（170 页，DOI 10.6028/NIST.SP.800-57pt1r5）

**关于测试密钥（A4 的直接依据）**：

> "Many applications or systems are provided by the manufacturer with keying material
> that is used to test that the newly installed application/system is functioning
> properly. **This test keying material shall not be used operationally.**"
> —— §8.1.4，印刷页 92

**关于「一把钥用到底」的影响面（A2 的直接依据）**：

> "The worst form of key compromise is one that is not detected. … A key management
> system should be designed to mitigate the negative effects of a key compromise;
> the system should be designed so that **the compromise of a single key compromises
> as little data as possible**. … The intent is to avoid building a system with
> catastrophic weaknesses."
> —— §5.5.2，印刷页 51

> "When a key is compromised, all use of the key to apply cryptographic protection to
> information … **shall cease**, and the compromised key **shall be revoked**."
> —— §5.5，印刷页 49

> "**The continued use of a compromised key shall be limited to processing information
> that has already been protected.**"
> —— §5.5，印刷页 49

**关于密钥保护**：

> "Confidentiality protection **shall** be provided for all secret key information
> (i.e., key information that is intended to be kept secret, such as symmetric (secret)
> keys …)."
> —— §6.1，印刷页 33

> "The following procedures are usually involved: 1. Limiting the amount of time that
> a secret symmetric or asymmetric private key is in plaintext form; 2. **Preventing
> humans from viewing plaintext secret** symmetric and asymmetric private keys;
> 3. Restricting plaintext secret and private keys to **physically protected
> 'containers'** …"
> —— §5.5.2，印刷页 50

### ⚠️ 引用边界

1. **SP 800-57 没有「禁止在源码中硬编码密钥」的条文。** 复核者全文计数：
   `hardcod` / `hard-cod` = 0、`source code` = 0、`compil*` = 0、`obfusc*` = 0、
   `reverse engineer` = 0。
   ⇒ 本报告**不声称**它有这样的条文。真正能用的是 §8.1.4（测试钥不得用于生产）
   与 §5.5.2（单钥影响面最小化）。
2. **它是美国联邦密钥管理指引**，不是移动应用安全标准，也不针对 iOS。
   把它映射到移动 App 是**读者的推断**，不是 NIST 的结论——本报告如实标注。

## 3. ATS（App Transport Security）

### 3.1 ATS 是什么

**出处**：`developer.apple.com/documentation/security/preventing-insecure-network-connections`
与 `…/information-property-list/nsapptransportsecurity/nsallowsarbitraryloads`

> "ATS requires that all HTTP connections made with the URL Loading System—typically
> using the URLSession class—use HTTPS."

> "The only action your app must take is to use secure URLs, like those beginning with
> `https`. Otherwise, ATS denies the connection and prints a console message:"

> "App Transport Security has blocked a cleartext HTTP (http://) resource load since it
> is insecure. Temporary exceptions can be configured via your app's Info.plist file."

> "A Boolean value indicating whether App Transport Security restrictions are disabled
> for all network connections."

### 3.2 关掉它意味着什么（**A3 加重指控的直接依据**）

> "Disabling ATS means that unsecured HTTP connections are allowed. **HTTPS connections
> are also allowed, and are still subject to default server trust evaluation** …
> However, **extended security checks—like requiring a minimum Transport Layer Security
> (TLS) protocol version—are disabled.** Without ATS, you're also free to loosen the
> defa[ult trust evaluation]…"

**这一段是 A3 的核心**：它同时证明了
①明文被允许 ②TLS 校验仍在 ③**TLS 下限等扩展检查被关闭**。

### 3.3 Apple 自己的警告 + App Store 审查要求

> "**You must supply a justification during App Store review if you set the key's value
> to `YES`** … Use this key with caution because **it significantly reduces the security
> of your app**. In most cases, it's better to upgrade your servers to meet the
> requirements imposed by ATS, or at least to use a narrower exception."
> —— NSAllowsArbitraryLoads 的 "Important" 说明

**意义**：Apple 自己说这个键「**显著降低应用安全性**」，且**必须**提交理由。
本 App 用了**最宽的全局开关**，而不是任何一项窄例外。

### 3.4 「忽略陷阱」（多数分析会搞错）

> "In iOS 10 and later and macOS 10.12 and later, the value of the
> `NSAllowsArbitraryLoads` key is **ignored**—and the default value of `NO` used
> instead—if any of the following keys are present in your app's Information Property
> List file:"

⇒ 若同时存在 `NSAllowsArbitraryLoadsInWebContent` / `NSAllowsLocalNetworking` /
`NSAllowsArbitraryLoadsForMedia`，该键**不生效**。
**本样本四键全无**（已实测），故该键**完全生效**。

## 4. 正面答案：密钥应该放哪

> **说「不应该」就必须答「应该怎样」。**

**出处**：`developer.apple.com/documentation/security/storing-keys-in-the-keychain`、
`…/security/protecting-keys-with-the-secure-enclave`、
Apple Platform Security《Keychain data protection》

> "**The keychain is the best place to store small secrets, like passwords and
> cryptographic keys.**"

> "Many apps need to handle passwords and other short but sensitive bits of data, such
> as keys and login tokens. **The keychain provides a secure way to store these
> items.**"

> "Keychain items are encrypted using two different AES-256-GCM keys: a table key
> (metadata) and a per-row key (secret key)."

> "The metadata key is protected by the Secure Enclave but is cached in the Application
> Processor to allow fast queries of the keychain. **The secret key always requires a
> round trip through the Secure Enclave.**"

> "ACLs are evaluated **inside the Secure Enclave** and are released to the kernel only
> if their specified constraints are met."

> "The Secure Enclave is a hardware-based key manager that's isolated from the main
> processor … When you protect a private key with the Secure Enclave, **you never handle
> the plain-text key**, making it difficult for the key to become compromised."

**对照本 App**：密钥以明文写在 H5 文件里（`Utf8.parse("385f…")`），
**既不在 Keychain，也不在 Secure Enclave，甚至不在 native 层**——
它就是一段纯文本，`grep` 即得。

## 5. 加密算法本身（用于确认「AES-256 没问题」）

**出处**：CryptoJS 官方文档 `cryptojs.gitbook.io/docs`

> "CryptoJS supports AES-128, AES-192, and AES-256. **It will pick the variant by the
> size of the key you pass in.**"

> "CryptoJS supports the following modes: CBC (the default), CFB, CTR, OFB, **ECB**.
> And CryptoJS supports the following padding schemes: Pkcs7 (the default)…"

**用途**：确认本报告对代码的解读准确——
`Utf8.parse` 传 32 字节 ⇒ AES-256；`mode: ECB` + `pad.Pkcs7` ⇒ 无 IV 的确定性加密。

## 6. 引用纪律（本报告自我约束）

1. **每条「不应该」配可点开的原文**；
2. **禁止写「业界共识无需引文」**；
3. **二手转写不算**——必须回原文核（本轮就抓到「ECB 缺乏扩散」被误挂 NIST 名下）；
4. **区分「标准原文」与「我们的解读」**——如 SP 800-57 到移动 App 的映射；
5. **取不到就写「未取得」**——中国标准正文属此类（见 §0）；
6. **正面答案也要给**——不能只说「不该硬编码」，要说「该放 Keychain / Secure Enclave」。

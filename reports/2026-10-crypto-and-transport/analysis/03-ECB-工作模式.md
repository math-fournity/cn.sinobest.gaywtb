# ECB 工作模式：AES-256 到底有没有问题？

> 主报告 §2.5 的完整版。回答一个具体疑问：
> **「ECB 在 AES-256 这种情况下，到底是不是有问题？」**
>
> 短答：**有问题，而且密钥长度救不了它。** 下面解释为什么。

---

## 1. 先分开两件常被混为一谈的事

| | 是什么 | 本 App 的选择 | 有没有问题 |
|---|---|---|---|
| **算法** | AES（高级加密标准） | AES-256 | ✅ **没问题**，是当今最强对称加密之一 |
| **密钥长度** | 128 / 192 / 256 位 | 256 位 | ✅ **没问题**，最高档 |
| **工作模式** | 怎么把多块数据串起来加密 | **ECB** | ❌ **问题在这里** |

**关键认知**：AES-256 是安全的。**问题不在算法，不在长度，在「怎么用它」。**

---

## 2. 为什么需要「工作模式」

AES 一次只能处理**固定大小的一块**（16 字节）。数据比 16 字节长时，需要一个
规则规定「多块怎么处理」——这就是工作模式。

| 模式 | 做法 | 同一明文每次加密 |
|---|---|---|
| **ECB**（电码本） | 每块**独立**加密，同一密钥、同样方式 | **永远得到同一密文** |
| **CBC** | 每块先与前一块的密文异或，再加密（需随机 IV） | 每次不同 |
| **GCM** | 计数器模式 + 认证（推荐） | 每次不同，且能防篡改 |

**ECB 的比喻**：一本「电码本」——`"AAAAAAAAAAAAAAAA"` 永远翻译成同一个结果。

---

## 3. 三个后果（都可以亲手复现）

> 以下数字全部用**本 App 的真实密钥与真实模式**算出。
> 复现：`python3 ../code/ecb_demo.py`

### 3.1 后果一：相同明文 → 相同密文

```
明文 "Passw0rd!2024"（用户 A） → 3e29a48221c4faf1b685ec5b5e5eaa57
明文 "Passw0rd!2024"（用户 B） → 3e29a48221c4faf1b685ec5b5e5eaa57
                                 ↑ 完全相同
```

**实际影响**：

- 服务端日志里两个账号的密码密文一模一样 → 看日志的人立刻知道「这两人同密码」；
- 网络中间设备、代理、任何截获密文的一方都能做这个比对；
- **这不需要破解 AES。**

### 3.2 后果二：短且可枚举的字段可直接还原

```
明文 "13800138000" → 密文 cd641daa9dae94ffd9fa34f1c8ad4add

攻击者离线把可能的手机号逐个加密、比对：
  1001 个候选内命中 → 还原出 13800138000
```

**为什么这比「暴力破解」严重得多**：

- 暴力破解 AES-256 需要 2^256 次运算，**物理上不可能**；
- 但这里攻击者**不需要破解 AES**——他只需要**做一次加密运算**去比对；
- 更关键：**ECB 没有随机量（IV），所以整张「号码→密文」对照表可以预先算一次、
  永久复用**，与目标是谁无关。

### 3.3 后果三：明文结构泄露

```
明文:  [AAAAAAAAAAAAAAAA] [BBBBBBBBBBBBBBBB] [AAAAAAAAAAAAAAAA]
密文:  [f5f151e9…]        [ef3049db…]        [f5f151e9…]
                                              ↑ 与第 1 块相同
```

明文里重复的 16 字节块，密文里也必然重复。著名的「ECB 企鹅图」就是这个原理：
加密后的图片轮廓依然清晰可辨。

---

## 4. 正面回答：「AES-256 这么长还不够吗？」

**这个直觉错在哪**：它假设「攻击 = 破解算法」。但 ECB 的攻击**全部绕开了算法**。

| 攻击方式 | 需要破解 AES-256 吗 | 受密钥长度影响吗 | 受模式影响吗 |
|---|---|---|---|
| 相同明文比对 | ❌ 不需要 | ❌ 不受影响 | ✅ **是** |
| 可枚举字段还原 | ❌ 不需要（只需一次加密运算） | ❌ 不受影响 | ✅ **是** |
| 结构泄露 | ❌ 不需要 | ❌ 不受影响 | ✅ **是** |

**256 位密钥保护的是「从密文反推密钥」这件事**——而上面三种攻击**根本不需要密钥**。

所以「AES-256 + ECB」这个组合的准确评价是：
**用了一把最强的锁，但把钥匙插在门上，还把所有门都做成同一个样子。**

---

## 5. 那「AES-256 + ECB」到底算不算失范？

### 5.1 从工程角度：算

| 判据 | 说明 |
|---|---|
| 加密**用户口令** | 口令是低熵、可枚举的，ECB 使其可被字典攻击——这是教科书级的错误 |
| 加密**手机号** | 11 位数字，空间约 10^10，ECB 使其可离线穷举 |
| 加密**验证码** | 通常只有 4~6 位数字，空间更小，ECB 下几乎等于明文 |

### 5.2 从规范角度：需要小心措辞（见 §6）

NIST SP 800-38A §6.1 原文：

> "In the ECB mode, under a given key, any given plaintext block always gets encrypted
> to the same ciphertext block. **If this property is undesirable in a particular
> application, the ECB mode should not be used.**"

**但必须同时声明**（否则构成过度主张）：

1. SP 800-38A 在印刷页 1 自述 *"neither a standard nor a guideline, and as such, is
   neither mandatory nor binding on Federal agencies"* —— **它是建议性文献**。
   本报告只写「NIST 建议此类场景不应使用 ECB」，**不写「违反 NIST 标准」**。
2. 该文件**全文不含** "diffusion" / "short data" 等表述（独立验证者全文 grep 零命中）。
   「ECB 缺乏扩散、只适合短数据」是**密码学教科书通说，不是该文件原句**——
   不得挂在该文件名下。

### 5.3 从「能辩护」角度：对方辩护不了

问：对方技术团队在会议室里能不能为「用 ECB 加密用户口令」辩护？

**不能。** 因为：

- 「我们不知道 ECB 有问题」→ 不合理，这是密码学入门内容；
- 「我们密钥够长」→ 见 §4，密钥长度与这三种攻击无关；
- 「我们传输层有 TLS」→ 但这把钥是**客户端加密后上传**，TLS 保护的是传输段，
  密文在服务端仍是确定的；
- 「我们有其他防护」→ 无法解释为何同一口令产生同一密文。

## 6. 正确做法

| 场景 | 正确做法 |
|---|---|
| 加密用户口令 | **不要加密口令**——用慢哈希（Argon2 / scrypt / bcrypt / PBKDF2） |
| 加密需还原的字段（如手机号） | **AES-GCM**（推荐，含完整性校验）或 **AES-CBC + 随机 IV** |
| 密钥管理 | 密钥不进包——服务端协商 / 系统 Keychain / Secure Enclave 派生 |

> **本 App 自己就有反例可用**：云从 SDK 的 `cw_aes_encodeContent:forKey:` /
> `cw_sm4_encode:byKey:` 是**参数化设计**（正式钥由调用方传入），
> 说明厂商知道正确做法；是集成方把钥写死在了 H5 层。

## 8. 复现

```bash
# 方式一：跑本目录的脚本（推荐，有讲解）
python3 ../code/ecb_demo.py

# 方式二：只用 openssl，手工验证
# 注意：该 App 的钥是 32 个 ASCII 字符，不是 32 位 hex。
#       openssl -K 要 hex，必须先转换；直接传 ASCII 会变成 AES-128。
KEYHEX=$(printf '%s' '385f33cb…9081ab7' | xxd -p -c 256)
echo ${#KEYHEX}     # 应为 64

# 同一密码两次加密 → 密文相同
printf 'Passw0rd!2024' | openssl enc -aes-256-ecb -K "$KEYHEX" -nosalt | xxd -p -c 256
# 期望 3e29a48221c4faf1b685ec5b5e5eaa57

# 重复明文块 → 重复密文块
printf 'AAAAAAAAAAAAAAAABBBBBBBBBBBBBBBBAAAAAAAAAAAAAAAA' | \
  openssl enc -aes-256-ecb -K "$KEYHEX" -nosalt -nopad | xxd -p -c 256
# 期望 f5f151e9…ef3049db…f5f151e9…（第 1 块 == 第 3 块）
```

> `xxd -p` 默认每 60 字符换行会截断 hex，务必加 `-c 256`。

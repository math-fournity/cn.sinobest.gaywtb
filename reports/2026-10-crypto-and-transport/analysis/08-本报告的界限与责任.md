# 本报告的界限：我们没有破壳，也不公开密钥

> 这一节回答一个必须先说清的问题：
>
> **你们把别人的密钥问题公开出来，这样做对吗？**
>
> 答案是：**我们公开的是「隐患存在」这件事，不是密钥本身。**
> 这两者之间有本质区别，本文件把它讲清楚。

---

## 1. 先说我们**没有**做什么

| 我们没做 | 说明 |
|---|---|
| ❌ **没有破解任何加固壳** | 本报告分析的样本是**社区已公开流通的解密 dump**（`cryptid=0`），不是我们脱的壳。取证过程见 [02 号文档](02-方法论与自我推翻记录.md) |
| ❌ **没有上传任何 IPA** | 本 repo 只含文本、脚本与机读结果，**不含任何 App 二进制或安装包** |
| ❌ **没有公布完整密钥** | 报告中所有密钥**已脱敏**（保留前后缀用于定位，中间打码）。详见 §3 |
| ❌ **没有接触任何服务器** | 纯静态分析，未运行该 App、未访问其任何服务端 |
| ❌ **没有利用这些密钥做任何事** | 没有解密任何真实用户数据，没有尝试登录 |

---

## 2. 关键事实：这把密钥**早就不是秘密了**

这是本节最重要的一段。

### 2.1 获取门槛极低

任何一个想拿到这把密钥的人，**今天就能拿到**，路径是：

```
1. 网上搜索「公安一网通办 解密 IPA」或类似关键词
   → 多个第三方站点提供已解密的 IPA（非苹果官方渠道）
2. 下载对应版本（1.2.28）
3. unzip 解包
4. grep 一下，密钥就出来了
```

**整个过程不需要任何密码学知识，不需要逆向工程，不需要脱壳。**

在 AI 辅助下，第 3~4 步甚至可以一句话完成。

### 2.2 这把密钥已经公开了很久

| 事实 | 值 |
|---|---|
| App 首次上架 | **2021-12-06** |
| 当前版本发布日期 | 2023-11-20 |
| 本报告所审版本 | 1.2.28 |

**从 2021 年 12 月第一个版本起，这把密钥就随每一个安装包分发出去。**
它不是「今天被我们发现的秘密」，而是**已经存在了四年多的公开信息**。

### 2.3 所以，问题不在「谁公开了它」

**如果**这把密钥原本被某种有效的保护措施（如加固壳、服务端下发）保护着，
而我们费尽力气破壳、提取、再公开——**那确实是不对的**。

**但事实不是这样。** 事实是：

- 它就在明文 JavaScript 里（H5 层无混淆、无加密）；
- 任何人拿到包就能读；
- 包在全球分发（美区/港/日/新 App Store 均在架，见主报告）；
- 解密 dump 在第三方站点公开流通。

**⇒ 这把密钥的暴露，与我们的报告无关。我们的报告只是把一件早已存在的事
指了出来。**

## 3. 我们的处理方式：报告位置，不报告密钥

### 3.1 报告里密钥是脱敏的

本 repo 中所有密钥均以如下形式出现：

```
385f33cb…9081ab7
```

**保留前 8 位与后 7 位**，中间打码。这个形式：

- ✅ **足够定位**——配合文件路径与字节偏移，能确认「就是这一把」；
- ❌ **不足以直接使用**——无法拿去解密任何东西。

### 3.2 但我们保留了完整的定位信息

脱敏**不影响可复核性**。任何拿到同版本 IPA 的人，可以在 30 秒内自己取到密钥：

```bash
# 1. 解包
unzip -q cn.sinobest.gaywtb-1.2.28-Decrypted.ipa -d out/

# 2. 定位文件（字节偏移 9485）
#    Payload/公安一网通办.app/www/p__login__Login.js

# 3. 取出密钥（32 个 ASCII 字符，不是 32 位 hex）
grep -o '[0-9a-f]\{32\}' \
  "out/Payload/公安一网通办.app/www/p__login__Login.js" | head -1
```

**这就是我们想要的效果**：报告的读者（尤其是开发者与主管部门）拿到对应版本后，
**借助 AI 敲几行命令，就能自己定位到密钥所在位置并验证我们的结论**——
而**不需要我们替他们把密钥抄一遍**。

### 3.3 为什么这样更好

| 做法 | 后果 |
|---|---|
| 报告里贴完整密钥 | 这份报告**本身变成密钥的分发渠道**；即使原 App 修好了，报告里的密钥仍然有效（因为它已被写进无数 fork、缓存、搜索引擎索引） |
| **报告里脱敏 + 给定位方法**（本报告的做法） | 复核能力**不受影响**（30 秒可自取），但报告不承担「扩散密钥」的责任 |

**关键区别**：我们提供的是**「怎么找到它」**，不是**「它就是什么」**。
前者是审计方法，后者是泄露。

## 4. 我们为什么要公开这件事

**因为不公开的代价更大。**

### 4.1 这个隐患已经存在四年

如 §2.2 所述，密钥自 2021 年 12 月起就随包分发。**四年多的时间里**：

- 任何拿到包的人都能读到它；
- 它保护的是**用户的登录密码、手机号、验证码**；
- 而且用的是 ECB（见 [07 号文档](07-为什么传密码不能用ECB.md)）——
  即使密钥保密，这个模式本身也会泄露信息。

**⇒ 真正的风险不是「我们说了」，而是「它一直在那里，而没人说」。**

### 4.2 指出问题的目的，是让它被修好

本报告的读者定位是**开发者与主管部门**。他们要的是：

1. **确认问题存在**（我们的证据链）；
2. **知道问题在哪**（文件 + 字节偏移 + 指令地址）；
3. **知道怎么修**（[07 号文档 §7](07-为什么传密码不能用ECB.md#7-正确做法说不应该必须答该怎样)）。

**一份不指出问题的报告，不会让问题消失，只会让它继续存在。**

### 4.3 一个必须承认的权衡

公开这类问题**确实有风险**：它可能被不怀好意的人利用。

但我们认为，在这个具体案例里：

| 因素 | 判断 |
|---|---|
| 信息的新鲜度 | **零**——四年多前就公开了 |
| 获取难度 | **极低**——搜索 + unzip + grep |
| 不公开的收益 | **无**——攻击者早就知道，只有用户和监管不知道 |
| 公开的收益 | **修复的可能** |

**⇒ 在这种情况下，「不公开」保护的不是用户，而是问题的存在本身。**

## 5. 我们给自己定的纪律

| 纪律 | 落实 |
|---|---|
| 不公开完整密钥 | ✅ 全文脱敏（§3.1） |
| 不上传 IPA | ✅ repo 内无二进制 |
| 不利用密钥做任何事 | ✅ 未解密任何真实数据 |
| 不接触服务器 | ✅ 纯静态 |
| 保留完整可复核性 | ✅ 文件 + 偏移 + 复现命令 |
| 明确不主张的事项 | ✅ 主报告 §6 |
| 撤回证据不足的结论 | ✅ 已撤回 5 次（[02 号文档](02-方法论与自我推翻记录.md)） |

---

## 6. 一句话总结

> **我们不是费尽心思去破壳、然后公开别人的密钥。
> 我们是把一件早已存在、且任何人都能轻易发现的安全隐患，认真地指了出来。**

如果这把密钥是被有效保护着的、需要破解才能取得——那我们不该公开。
**但它不是。它一直躺在明文里，跟着每一个安装包发往全世界。**
